GPS Spoofing System — SDR Signal Injection and Drone Position-Control Verification Report

A bench setup that transmits a synthetic GPS radio signal at a drone and checks, against two independent readouts, whether the flight controller actually believed it.

01Abstract

This spoofing system builds a fake GPS radio signal and transmits it at a target drone through a software-defined radio (an SDR — a radio whose behaviour is set entirely by software, not fixed hardware). The drone's own GPS receiver cannot tell our signal apart from a real satellite, and simply locks onto whichever one is louder. Once it is ours, we can tell the receiver it is anywhere we like.

The interesting part is what happens next. A drone flying in GUIDED or LOITER mode is always trying to correct its position back to where it should be. If we feed it a slow fake drift to the north, it does not fly north — it flies south, fighting an error that only exists inside its own GPS feed. That reversal is the core effect this SDR-based spoofing system is built to demonstrate and measure.

This document walks through the complete chain — pulling real satellite data, building a flight path, turning it into a radio signal, transmitting it, and checking the real outcome on two separate screens — and is honest about the rough edges we found and fixed along the way, not just the clean runs.

02Objective

  • Build a repeatable bench test that spoofs a real ArduPilot flight controller's GPS input over the air, using the real GPS L1 frequency.
  • Prove — not assume — that the flight controller accepted the fake position, by reading its actual reported fix rather than guessing from a timer.
  • Cross-check that reading against a second, independent source: Mission Planner's own live telemetry.
  • Use the drift-then-correct behaviour to test how a drone under GUIDED/LOITER control responds to slow position spoofing, as a stand-in for testing GNSS spoofing detection and EKF failsafe thresholds.

03Problem Statement

Before this round of work, the spoofing system could transmit a spoofed signal, but the terminal reporting whether it had "locked" was not actually reading the drone — it printed success once a fixed amount of time had passed, regardless of what the flight controller was really doing. That meant every "it worked" claim was a guess dressed up as a measurement. On top of that, the daily satellite data file had to be renamed by hand every single day, and there was no second way to confirm the reported position besides trusting our own code.

The problem, plainly: we could transmit a spoofed GPS signal, but we could not honestly prove the drone had believed it. This report documents the fix.

04Methodology

Every test run follows the same six stages, in this order:

  1. Pull today's real satellite data. Every GPS satellite broadcasts orbit and clock data about itself, called ephemeris. sync_gps.sh downloads today's real file (for example brdc2030.26n) from NASA's CDDIS archive. Without fresh ephemeris the fake signal would describe satellites that are not really where they should be, and the receiver would throw it out as nonsense.
  2. Connect Mission Planner and load the helper script. Normal Auto Connect, then open Mission Planner's Scripts tab and run mp_scripts/gps_udp_forward.py. This script runs inside Mission Planner itself and hands its own live GPS numbers to our monitor over the network.
  3. Decide the flight path. One of three shapes — a straight walk to one target, a repeating four-direction drift around a start point, or instant jumps between a list of cities. Whichever shape, the output is the same: a plain list of "at this time, be at this exact lat/lon/altitude."
  4. Turn the path into a radio signal. gpssim, built on the open-source gps-sdr-sim project, reads the real satellite data and the flight path, and works out — for every satellite that would be visible — exactly what its signal should look like if the receiver really were moving along that path. It sums all of those signals into one stream of raw samples.
  5. Transmit continuously on the real GPS frequency. tx_gpssim plays that sample stream through a USRP B210 SDR on 1575.42 MHz — the genuine GPS L1 frequency — in a loop that keeps the radio open the whole time, so there is no restart gap.
  6. Watch the real result on two independent screens. A monitor script asks the flight controller, over MAVLink, what it actually believes its position is, and separately asks Mission Planner the same question through the helper script, then prints the honest answer every second.

06Multi-Directional Spoofing Techniques

Beyond the single-target walk described in §4, the codebase includes several purpose-built scripts for different spoofing patterns. All of them work on the same underlying principle from §8: the drone corrects opposite to whatever fake drift direction it is told about.

Figure 3 — 4-direction drift cycle: CENTER → NORTH → CENTER → EAST → CENTER → SOUTH → CENTER → WEST → CENTER, then repeats. Each direction starts from the same known-good reference point, at ~200 m offset and ~2.5 m/s. The 8-direction script (multidirectional_spoof.py) runs the same pattern with four extra intercardinal legs (NE, SE, SW, NW).

ScriptPatternNotes
multi_drift.py / run_spoof_full.sh cycle4-direction cycle: N → E → S → W, returning to centre each time~200 m offset, ~2.5 m/s ramp, one gpssim call per leg with no transmission gap
multidirectional_spoof.py8-direction cycle: N → NE → E → SE → S → SW → W → NWSupports --ramp-speed 0 (instant GPS teleport per epoch) or a smooth ramp (5–8 m/s); finer directional coverage than the 4-direction cycle
waypoint_spoof.py / run_spoof_full.sh switchInstant jumps between named real-world coordinates (e.g. six Indian cities, or a list of local landmarks)Each stop: ramp to anchor → hold → ramp to waypoint → hold → ramp back; used to test whether the flight controller's safety checks catch an impossibly large jump
gps_joystick.pyManual, operator-steered drift in real time (WASD / arrow keys, 8 directions plus altitude)Same opposite-direction rule applies live — useful for interactively demonstrating the effect rather than running a fixed pattern
gps_coldstart.pyNot a drift pattern — a pre-step run before the othersSends a MAVLink UBX-CFG-RST full cold-start command to the receiver, clearing its cached almanac/ephemeris/time so it does not reject our simulated time as "wrong satellite position"
Two different drift-speed ceilings appear in the codebase, both under the receiver's threshold on purpose: the 4-direction cycle scripts default to ≈2.5 m/s against a documented ~3 m/s EKF sanity limit, while the 8-direction and joystick scripts document ArduPilot's velocity-innovation rejection threshold at roughly 5–10 m/s and default to 2–8 m/s ramps. Both stay safely below the point where the EKF would flag the GPS jump as physically impossible and ignore it (§8).

Why cold-start matters: a GNSS receiver that already has recent almanac/ephemeris data "knows," roughly, where each satellite should be right now. If our spoofed signal claims a satellite is somewhere that does not match the receiver's own expectation for that time, it can reject the signal instead of tracking it. Clearing that cached state first (via gps_coldstart.py) removes that expectation, so the receiver accepts whatever signal it hears — ours included.

07System Internals — How Each File Works

This section explains, file by file, what the code that drives the SDR transmitter and the drift/waypoint logic actually does internally, so the pipeline in Figure 1 is not a black box.

run_spoof_full.sh — orchestrator

This is the script an operator actually runs. It takes a gain value in dB and an optional mode word (cycle or switch; no word means a single walk to one target).

  • Works out today's date and satellite-data filename on its own (no hand-editing).
  • Converts the chosen start/target/waypoint coordinates into a time-stamped trajectory, in chunks, so the next chunk can be generated in the background while the current one is transmitting — this removes the gap that used to exist between chunks.
  • Calls gpssim with --l1-gain "${GAIN}" and the current ephemeris + trajectory files to build the IQ sample file for that chunk.
  • Calls tx_gpssim to transmit that IQ file, and loops forever (cycle/switch modes) or until the target is reached and held (normal mode).
  • Launches spoof_monitor.py alongside the transmission so the terminal status is live, not guessed.
./run_spoof_full.sh 75 # single walk: start → target, then hold ./run_spoof_full.sh 85 cycle # loop N → E → S → W around start, forever ./run_spoof_full.sh 85 switch # instant-jump across a list of cities, forever
gpssim.c — signal generator (built on gps-sdr-sim)

Reads the ephemeris file (real satellite orbits/clocks) and the trajectory file (our fake path), and for every GPS satellite that would be visible from that path at that time, computes the exact code phase, Doppler shift (frequency change caused by relative motion), and navigation data bits that satellite's real signal would carry. It adds all of the satellites' signals together into one combined stream of 16-bit I/Q samples at 2.6 Msps (million samples per second) — this file is the actual fake GPS waveform, before any radio hardware is involved.

tx_gpssim.cpp — radio driver

Takes the IQ sample file from gpssim and streams it out through the USRP B210 using the UHD driver library. Three lines in the code set the actual radio behaviour:

usrp->set_tx_rate(samp_rate); // 2,600,000 samples/sec usrp->set_tx_freq(uhd::tune_request_t(1575.42e6)); // real GPS L1 frequency usrp->set_tx_gain(gain); // operator-supplied, e.g. 75 or 85 dB

It keeps the radio hardware open across the whole run (a "gapless loop") so there is never a silent gap where the receiver could notice the real sky again.

mp_scripts/gps_udp_forward.py — Mission Planner side-channel

Not a normal Python script — it only runs inside Mission Planner's own IronPython scripting console (Scripts tab → Open → Run), using Mission Planner's built-in cs object to read whatever Mission Planner itself currently displays.

lat = cs.lat; lon = cs.lng; alt = cs.alt fix = int(cs.gpsstatus) # 0/1=No Fix, 2=2D, 3=3D, 4=3D+DGPS, 5/6=RTK sats = int(cs.satcount) sock.sendto(("%.7f,%.7f,%.2f,%d,%d,%.3f" % (lat,lon,alt,fix,sats,time.time())).encode(), ("127.0.0.1", 5051))

It fires this UDP packet about five times a second to port 5051, regardless of whether Mission Planner is connected by USB, radio, or auto-connect — giving us a second, independent read of the drone's believed position that does not depend on our own MAVLink connection being correct.

spoof_monitor.py — terminal status reader

Runs two readers at once, in a background thread each:

  • A MAVLink reader that requests and reads the flight controller's own GPS_RAW_INT message — the same message ArduPilot itself uses internally.
  • A UDP listener on port 5051 for the Mission Planner side-channel above.

Whichever source last delivered data drives the printed line. Distance between our transmitted target and the receiver's reported fix is computed with the Haversine formula (great-circle distance between two lat/lon points). Status only becomes SPOOFED — LOCKED once there is a real 3D fix and that fix is within 15 m of what we are transmitting — never on a timer.

08Why the Real Drone Flies the Opposite Way

This is the single most counter-intuitive part of the whole spoofing technique, so it is worth explaining slowly, in plain language.

A drone in GUIDED or LOITER/POSHOLD mode is always trying to hold a target position. Its EKF (Extended Kalman Filter — the internal algorithm that blends GPS with the gyroscope, accelerometer, and barometer into one best-guess position) takes whatever GPS reports and folds it in with the other sensors. If GPS says the drone has drifted, the flight controller commands the motors to fly back toward where it should be.

The other sensors feel nothing, because nothing is physically pushing the airframe — only the GPS number is changing, slowly, because we are changing it. As long as that fake drift stays under about 3 m/s (the flight controller's own "is this even physically possible" sanity check on GPS), the EKF treats it as ordinary motion and accepts it. So if we transmit a fake 200 m drift to the north, the flight controller believes it really is 200 m north of where it should be — and commands the motors south, to correct.

Figure 4 — Fake drift in, opposite real motion out. The correction loop repeats continuously while the fake drift keeps transmitting, which is what physically walks the aircraft off its original spot.

Why the 3 m/s speed cap matters: faster than that, the EKF's own sanity check flags the GPS jump as physically impossible and ignores it outright — and this whole corrective-flight effect never triggers. That is why the drift scripts default to roughly 2.5 m/s (about 9 km/h), comfortably under the cutoff.

09Verification Setup — Two Independent Screens

The point of this whole exercise is not to trust our own code. Two separate sources are read and compared, live:

SourceWhat it readsPath
Mission PlannerHUD fix status, map position, GEO readout, Scripts console logIts own telemetry link → gps_udp_forward.py → UDP → our monitor
Our terminalGPS_RAW_INT.fix_type, lat/lon, distance to our transmitted targetMAVLink direct to the flight controller

A sample terminal line, read left to right:

16:56:14 ● SPOOFED — LOCKED #1 DRIFTING EAST→CENTER 17.604012 78.128775 3D 14.2m time status loop phase/direction TX lat/lon RX fix gap-to-target

At 16:56:14, on loop 1, while drifting from east back toward centre, we were transmitting 17.604012°N / 78.128775°E, and the drone's real GPS reported a 3D fix only 14.2 m away from that — close enough to count as locked.

"Locked" here means two different things stacked on top of each other: first the receiver's own radio chip has to find and track each satellite's signal (30–90 s from a cold start — why every run begins with a long hold), and only after that is our own software label (SPOOFED — LOCKED, within 15 m of target) meaningful at all.

10Signal Specifications

The exact commands, frequency, and power settings used, with the reason for each:

Carrier frequency1575.42 MHzThe real civilian GPS "L1" frequency. We transmit on the exact frequency every GPS receiver already listens on — nothing invented.
Signal typeL1 C/AThe standard civilian GPS code: a repeating 1023-chip pattern, unique per satellite, that any commercial receiver already knows how to read.

12Results — What We Actually Saw on the Bench

Test run: ./run_spoof_full.sh 75 cycle against a real ArduCopter flight controller, with Mission Planner's own script feeding back live coordinates.

StageTerminal readingWhat it meant
Just after startLINKED, NO GPS MSGConnected, GPS stream had not started flowing yet — expected at this stage

Two things flagged, not hidden:

  • Right after a restart, the drone briefly reported "Unhealthy GPS Signal" at a position roughly 130 km off, before settling back within about 30 seconds — normal receiver re-acquisition behaviour, not a code defect.
  • Near the 15 m cutoff, "locked / not locked" flickered back and forth while actively drifting — expected from a hard cutoff against a moving, slightly noisy number (addressed in §14).

Achievements this round:

  • Terminal status is read from the drone itself, not guessed from a timer, in all three run modes.
  • A second, independent source of real coordinates (Mission Planner's own scripting console) is now in place.
  • The daily hand-edit of satellite-data filename and date is gone.
  • Verified on real hardware: convergence to within ~2 m of the intended target, in all four compass directions.
  • Confirmed the SDR transmitter shuts down cleanly on an unexpected hardware disconnection.

14Future Work — Path to a Shareable Tool

  1. A proper build system — one build file, pinned library versions.
  2. A settings file instead of settings hard-coded in the script.
  3. Scheduled, alerting refresh of the satellite data.
  4. Smarter lock detection — buffer zone plus a filter for impossible readings.
  5. Structured logs (clean data files instead of screenshots).
  6. A safe SITL-based (Software-In-The-Loop, i.e. simulated aircraft) practice mode with no real radio or aircraft involved.
  7. Safety guardrails: gain ceilings, geofenced allowed coordinates, explicit confirmation before any real transmission.
  8. Support for more than one receiver/ground-station combination without changing code.

15Conclusion

The spoofing system now does what it was always meant to do, honestly: it transmits a real GPS L1 signal built from genuine satellite data, and it proves — against two independent readouts rather than a guess — whether the target flight controller believed it. The counter-intuitive corrective-flight effect (fake drift one way, real aircraft moving the opposite way) was reproduced and measured on real hardware in all four compass directions, converging to within about 2 metres of the intended target. The remaining rough edges (§13) are understood and have concrete next steps, not open questions.
